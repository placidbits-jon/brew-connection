# Brew telemetry and event pulse

Open `/demo/brews/blueberry-bloom-v60`. The historical series contains exactly 60 measurements beginning September 14, 2026 at 16:00 UTC. At second 30 flow rises from the brew's stored target of 4 g/s to 12 g/s. Water remains the independent seeded scale measurement: 120 g at that point. The water target interpolates the immutable revision linked on `USED_RECIPE`: 60 g at second 0, 180 g at 45, and 300 g at 90, giving 140 g at second 30. The API explicitly labels interpolation as an application calculation.

Replay queues a persistent `TelemetryRun` document with a unique run identity. The Aspire telemetry simulator polls the API, generates the deterministic 60 measurements and posts ten at a time, with a half-second pause between chunks, through a bounded ingestion endpoint. The chart can show the growing sample count. A run becomes complete only after all 60 stored timestamps are present. The API writes InfluxDB line protocol to ArcadeDB's native HTTP time-series endpoint. Replay records use the existing device tag (`replay-<runId>`); the historical device remains `scale-0`. Reads select one run. Repeating the same identity returns the same run, and ingestion reconciles existing timestamps before writing missing samples, including retries after a lost response. Run identities cannot be reused for a different brew. Reset removes replay jobs and samples together under the shared graph gate.

`/demo/pulse` displays the two-hour authored event window. Each minute's tasting count repeats 1, 2, 3, 4, 5: 120 samples, 360 tastings, twelve ten-minute buckets of 30, and native `ts.percentile(count, 0.95)` of 5. Event rate is the database SUM divided by the 120-minute window in the API: 3 tastings/minute. A separate native `ts.rate(water_grams, ts)` result is 4 g/s, demonstrating a rate of change on an appropriate cumulative measurement. Native 30-minute AVG/SUM downsampling returns four averages of 3 and totals of 90; this is query-time aggregation and does not delete raw measurements.

Starting the retention example creates the separate `DemoRetention` native type with one-day retention and one-minute compaction boundaries, and writes one recent and one two-day-old sample. Refresh after ArcadeDB's approximately 60-second maintenance interval: the count changes from two to one. The API does not delete the expired sample itself. Retention removes complete sealed blocks; the minute compaction interval keeps the old and recent samples in separate blocks. Authored historical series have no retention policy and remain available for future rehearsals.

SQL reads operate on native time-series storage with bounded timestamp and tag filters. The pinned 26.9.1 dedicated `/ts/query` raw projection was observed returning incorrect field positions when fields and multiple tags were supplied; the application therefore uses verified SQL reads. Native HTTP ingestion is unaffected. The inspector exposes actual executed statements, parameters and application calculation labels.

Reference: [ArcadeDB native time-series documentation](https://docs.arcadedb.com/arcadedb/concepts/timeseries).

Run `python3 scripts/verify-telemetry.py --api http://localhost:5130 --retention` with the Aspire worker running to verify the anomaly, golden buckets, validation and idempotent replay.
